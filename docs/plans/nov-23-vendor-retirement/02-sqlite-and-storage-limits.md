### SQL-06 파일 단위 이전

포크의 C `qiv_close_owned_fd`는 `close(2)`를 한 번 호출하고 errno를 되돌린다. `nix 0.31.3`의 `nix::unistd::close(File)`도 소유권을 소비하고 `libc::close`를 한 번 호출하며 `Errno`를 반환한다. `EINTR` 또는 다른 오류 뒤 fd 숫자를 재시도하지 않는다. ### SQLite 0.38 공개 VFS API 적합성 판정

현재 `libsqlite3-sys 0.38.2`의 공개 `sqlite3_vfs`/`sqlite3_io_methods` FFI에는 `sqlite3_vfs_find/register`, `xOpen/xDelete/xAccess/xFullPathname`, 파일별 `xClose/xRead/xWrite/xTruncate/xSync/xFileControl`, WAL용 `xShmMap/xShmLock/xShmUnmap`이 있다. 제품 소유 VFS 확장에서 순정 하위 VFS를 감싸면 DB/WAL의 선행 쓰기·truncate 승인, SHM map 요청 시 선행 보수적 예약, SQLite 이름 선택과 callback 오류 전달은 구현 가능하다. `rusqlite::Connection::open_with_flags_and_vfs`가 Catalog/Scratch의 연결 지점이다. 현재 C shim 자체가 이 공개 wrapper 패턴을 쓴다. [공개 FFI](../../../vendor/libsqlite3-sys-0.38.2/sqlite3/bindgen_bundled_version.rs) · [현행 shim](../../../vendor/libsqlite3-sys-0.38.2/quanta/quanta_capacity_vfs.c)

그러나 **순정 Unix VFS를 감싼 파일 단위 공개 hook만으로 현행 동등 계약 전체를 이전할 수 없다**. 하위 `sqlite3_file`의 실제 `unixFile.h`, `pShm->pShmNode->hShm`, 지연 POSIX close 목록, `unixShmRegionPerMap()` 반올림 값은 공개 `sqlite3_file` ABI가 아니다. 현재 witness는 `sqlite3.c`의 `unixFile`/`unixShm` 내부에 삽입되고, native close 경로도 amalgamation의 `robust_close`를 수정한다. 따라서 wrapper의 이름·경로 사전 검사와 재오픈 FD로는 **실제** DB/WAL/SHM inode·FD 일치, 동일 FD의 WAL recovery ceiling, 물리 retirement 시점 charge 해제, 정확한 SHM 증가 폭을 증명할 수 없다. 현재 포크도 parent 경로의 preflight 이후 retarget gap을 문서화한다. `sqlite3_file_control`과 `sqlite3_wal_hook`은 각각 파일 제어와 post-commit 알림이며 이 누락된 내부 증거를 제공하지 않는다. WAL frame/checkpoint batching은 SQLite 내부 write loop의 별도 amalgamation 패치로 공개 VFS callback 이전 대상이 아니다. [native witness](../../../vendor/libsqlite3-sys-0.38.2/quanta/quanta_native_witness.inc) · [패치 경계](../../../vendor/libsqlite3-sys-0.38.2/QUANTA_PATCH.md)

원 계약을 유지하려면 제품 소유 **완전한 POSIX VFS**에서 root FD에 고정한 `openat` 계열 열기, Unix lock/WAL SHM, descriptor·close 계측을 직접 구현하거나, 다음 절의 **공개 Unix syscall override 실험 경로**를 먼저 입증해야 한다. 전자는 감사 가능한 C 또는 Rust unsafe FFI 경계, 빌드·링크 소유자 및 Linux/macOS 별 동작 검증이 필요하다. 계약을 바꿀 경우에는 순정 VFS와 지원 Linux 배포의 root·quota 격리 및 앱 예약을 조합하고, 실제 FD 동등성·native physical retirement·선행 SHM 바이트 보장 같은 주장을 제거한 뒤 SQL-03/04/07/09의 대체 oracle과 장애 수용을 명시한다. 어느 경로도 결정·구현·제품 검증 전에는 VFS 퇴역 완료가 아니다. 단순 `publication_sqlite_vfs.rs` 이동이나 Cargo patch 삭제는 수용 불가다.

#### 공개 Unix syscall override 경로 · production 미연결

추가 소스 확인: `sqlite3_vfs` v3의 공개 `xGetSystemCall/xSetSystemCall`로 pinned Unix VFS의 `open`, `close`, `ftruncate`, `pwrite`, `unlink` 등을 바꿀 수 있다. `unixOpenSharedMemory`의 `-shm` FD도 `osOpen`을 거치고 `robust_close`/지연 close도 `osClose`로 끝나므로, 별도 제품 FFI crate가 실제 FD의 open/physical close를 기록하고 `open`을 root FD 기준 `openat`으로 수행할 **가능성**이 있다. DB/WAL 선행 승인은 named VFS wrapper의 `xWrite/xTruncate`, SHM 선행 승인은 `xShmMap`에서 수행하고 `open/pwrite/close` syscall witness와 대조해야 한다. 이 방식은 SQLite 내부 struct를 읽거나 amalgamation을 복사하지 않는다. 다만 SQLite 공식 C 헤더는 이 override를 optional **VFS 테스트 인터페이스**로 규정하고, 지원되는 syscall 이름과 동작이 버전마다 달라질 수 있다고 명시한다. [Unix syscall table](../../../vendor/libsqlite3-sys-0.38.2/sqlite3/sqlite3.c)

`/tmp/qiv_sqlite_syscall_poc.c`를 pinned `sqlite3.c`와 `clang -std=c11 -D_DEFAULT_SOURCE -O0 -I vendor/libsqlite3-sys-0.38.2/sqlite3 vendor/libsqlite3-sys-0.38.2/sqlite3/sqlite3.c /tmp/qiv_sqlite_syscall_poc.c -lpthread -ldl -lm -o /tmp/qiv_sqlite_syscall_poc`로 직접 연결하고 실행한 결과는 **VERIFIED**, exit 0이다. hook은 main DB/WAL/SHM open(`-shm` FD 1건), physical close, SHM 초기 `ftruncate(fd, 3)`, unlink를 관측했다. Rollback journal의 두 connection 중 하나가 lock을 보유한 상태에서 다른 connection을 닫자 `close` hook count는 9→9로 유지됐고 보유 connection commit 뒤 9→10이 됐다. 즉 native 지연 close의 실제 retirement를 hook으로 **관측 가능**했다(이 한 경합에 한함). **반례:** scope 1의 DB뿐 아니라 scope 0의 별도 SQLite DB도 같은 hook을 통과해 `unscoped_opens=5`였다. 테이블은 process-global이며 scope 밖 SQLite를 자동 격리하지 않는다. 초기 `ftruncate(fd, 3)`은 SHM의 최종 32 KiB 증가가 아니다. `unixShmMap`은 4 KiB 각 page 끝을 `seekAndWriteFd`로 기록하므로 `ftruncate`만 가로채는 구현은 SHM 선행 승인에 실패한다. PoC는 단일 스레드, 로컬 macOS, 정상 I/O만 실행했으며 다중 root·병렬 요청·worker thread·FD 재사용·fault 수용은 **NOT_RUN**이다. disposable PoC 파일은 checkout 밖에 두었고 제품 회귀 증거가 아니다.

**production 연결 gate:** (1) 별도 `quanta-index-sqlite-vfs` FFI crate가 공개 SQLite ABI 및 Unix syscall 이름·원본 포인터를 등록 시 검증하고 실패 시 닫힌다. Runtime crate의 `#![forbid(unsafe_code)]`는 유지한다. (2) 모든 open/stat/access/unlink 및 WAL/SHM 부수 파일이 root FD에 결속되고 `/dev/urandom` 같은 SQLite 보조 open만 감사 가능한 예외로 분리된다. `rename`은 pinned Unix override 테이블에 없으므로 해당 경로가 제품 워크로드에서 필요하면 wrapper 수준에서 별도 처리하거나 이 실험 경로를 기각한다. (3) process-global override가 다른 SQLite 소비자에 미치는 영향을 배제하거나 독립 engine process로 격리한다. TLS 요청 scope와 물리 FD→root/charge registry를 분리해 다른 thread의 deferred close도 FD 재사용 없이 정산한다. (4) `xShmMap`의 실제 반올림·`pwrite/mmap` 확장과 선행 예약·실제 FD/inode witness를 병렬·장기 pin·경로 교체·fault에서 검증한다. (5) macOS/Linux 서로 다른 Unix VFS 이름·syscall table을 별도 수용한다. 이 중 하나라도 불명확하면 SQL-03/04/07의 동등성은 **BLOCKED**이며 override를 production에 등록하지 않는다. 새 crate workspace member, `libsqlite3-sys` 단일 links 소유, C build/unsafe 감사와 Semantica 0.30 공급자 조율이 필요하므로 공용 manifest/lock 변경 전에는 연결하지 않는다.

#### 제품 소유 FD ledger 부분 구현

`crates/quanta-index-sqlite-fd-ledger/`를 standalone 안전 Rust crate로 추가했다. 실제 `open`과 `close`를 같은 mutex 안에서 호출하는 `open_with`/`close_with`, FD 번호와 단조 증가 generation, root/charge/device/inode witness를 보유한다. `release_owner`와 성공한 **물리** close 양쪽이 확인된 뒤 한 번만 retirement receipt를 발급한다. `EINTR`/`EBADF` 등 close 오류는 숫자 FD를 재시도하지 않고 기존 charge를 격리하며, 그 번호가 새 open에 재사용돼도 새 generation만 정산하고 이전 charge는 유지한다. `fstat` witness 실패는 열린 FD를 `Quarantined`로 기록해 refund하지 않는다. 초기 BTreeMap 구현의 open 뒤 allocation/OOM 틈을 제거하고, `try_reserve_exact`로 **open 전** 전체 slot을 확보하는 고정 Vec로 바꿨다. slot 소진은 syscall 전에 거절한다. open/witness/close closure가 panic하면 추적 불가능한 FD로 실행을 계속하지 않도록 프로세스를 abort한다. **이 ledger는 현재 SQLite syscall이나 PublicationFileCapacity에 연결되지 않았다.** `#[workspace]`로 독립 빌드되고 공용 `Cargo.toml`/`Cargo.lock` 및 Semantica 공급자를 수정하지 않았다. [ledger source](../../../crates/quanta-index-sqlite-fd-ledger/src/lib.rs)

`rustc --edition 2024 --test crates/quanta-index-sqlite-fd-ledger/src/lib.rs -o /tmp/qiv_fd_ledger_tests && /tmp/qiv_fd_ledger_tests`: **VERIFIED 6/6**. Deferred close, close-before-owner, EINTR, EBADF, FD 번호 재사용, witness 누락, slot 소진 시 open 미실행의 불변식만 검증했다. 실제 syscall interception·복수 thread/Root·SQLite locking/SHM·PublicationFileCapacity charge 환불은 **NOT_RUN**. 연결 시 발급 증거는 root FD에 고정한 실제 open의 `fstat` identity와 pre-reserved charge ID이고, 폐기 증거는 같은 generation의 실제 `close` 성공 및 논리 owner 종료다. FFI adapter가 `openat/fstat`와 `close`를 ledger closure 안에서 실행하고, 다른 코드가 같은 FD를 우회 조작하지 않음을 증명해야 한다. 기존 PublicationFileCapacity는 root FD에 anchored `openat`, `NativeOpenGuard`/`NativeReaderLease`, `max_open_handles`/`max_tracked_entries`와 불확실 close 격리를 제공해 재사용 대상이지만, SQLite Unix FD generation 테이블과 syscall callback owner는 제공하지 않는다. 새 고정 Vec의 backing도 기존 `WorkBudget.reserve_memory(..., Retained)` 같은 실제 memory grant에 아직 결속되지 않았다. `try_reserve_exact`는 allocator 실패를 조기에 반환할 뿐 제품 hard memory quota 입장을 증명하지 않는다. 비용은 프로세스 전역 syscall 직렬화와 O(설정한 최대 slot) retained backing이며, 오류 격리분은 재시작 재고 대조 전에는 환불되지 않는다. 현재 ledger는 물리 FD당 한 owner만 표현한다. SHM의 여러 connection lease와 SQLite lock 상태·WAL reader lifetime은 별도 owner/lock 모델이 필요하다. FFI callback의 `open_fd`가 성공한 FD를 반환 전에 임의 오류로 바꾸지 않는 것도 별도 감사 gate다. 이 prototype은 workspace에 편입하지 않으며 SQL-03/04/07 또는 포크 퇴역을 수용하지 않는다.

Semantica 공급자 경계도 별도 검증한다. 현재 Semantica의 `quanta-sqlite-native-reader`는 feature `native-worker-v1`에서 로컬 `libsqlite3-sys =0.30.0`과 `quanta-source-v1`을 선택하고, `quanta-runtime/sqlite-store`가 이 reader를 활성화한다. Q의 lexical crate는 `rusqlite 0.40` 계열 및 `libsqlite3-sys 0.38.2` `quanta-capacity-vfs`에 의존한다. 두 공급자가 같은 Cargo 최종 그래프에 들어가면 `links=sqlite3` 충돌 위험이 있다. 통합자가 Semantica의 실제 소비 feature 조합마다 `cargo metadata/tree --locked`로 단일 SQLite owner를 확인하고 0.30 native-reader 이관 경로를 먼저 정해야 한다. 어느 조합의 실행 연결이 실제로 충돌하는지는 이 트랙에서 **NOT_RUN**이다. ## 두 번째 변경 · 용량 집행 이전

1. 설치 담당이 실제 지원 Linux 배포에서 Root에 적용 가능한 파일시스템·볼륨 하드 한도를 하나 선정한다. SQLite DB/WAL/SHM, Native 객체, Lance 파일, scratch·staging, 같은 저장소를 쓰는 복구 임시 출력의 실제 마운트와 quota 귀속을 확인한다. 기존 E07 aggregate 한도를 여러 Root가 우회하지 않는 배치로 검증한다.
2. 앱 입장 예약과 배포 하드 한도를 SQL-03/09대로 구현한다. 동시성 때문에 사전 예약과 실제 점유량이 달라지면 배포 하드 한도가 막는다. 상태 경로가 집행 범위에 결속되지 않으면 배포를 활성화하지 않는다. 운영 구성에 적합한 집행 방법이 없으면 해당 배포의 VFS 퇴역 수용은 **BLOCKED**다.
3. 순정 SQLite VFS로 연결한다. WAL·내구성 설정과 트랜잭션 경계를 유지하고 `SQLITE_FULL`·하위 저장소 오류를 SQL-08대로 전달한다. 커밋·정산 결과는 실제 상태와 대조한다. native VFS의 파일별 영수증을 삭제할 때는 SQL-04/07의 관측·lifetime 대체와 계약 변경 여부를 먼저 확정한다.
4. Catalog, scratch, Native recovery·boot 진입점과 자원 정산에서 커스텀 feature 및 연결을 정리한다. 사전 거절과 native hook만 검사한 본문은 퇴역 근거를 남긴다. 게시 정합성·원복·정산을 검사하던 본문은 순정 경로에서 유지한다. ## 의존 순서와 수용 경계

1. SQL-01의 계측 보존/퇴역 결정을 고정한다. Catalog io_admission·connection/diagnostic·writer_cache, Scratch edit_write, core DiagnosticCounterV1, searchd trace_wire·recorder와 소비자를 함께 전환한다. registry rusqlite로 바꿀 때 기존 libsqlite3-sys VFS feature와 단일 SQLite links 소유자가 유지되는지 확인한다.
2. SQL-06의 공용 close를 독립화하고 기존 vendor helper import를 0으로 만든다. File drop만으로 치환한 상태는 수용하지 않는다.
3. SQL-03/04/07/09의 유지 불가능한 속성은 별도 I/O 구현 또는 명시적 제품 계약 변경으로 결정한다. SQL-11의 성능 회귀 허용 한도와 측정 profile을 실행 전에 고정한다. 실제 지원 Linux의 Root/mount/quota, 권한·기동 검증·재시작 지속성, 파일 수·논리 길이 장부와 maintenance reserve를 설계한다. 집행 가능한 OS hard quota가 없으면 해당 배포의 VFS 퇴역은 **BLOCKED**다.
4. SQL-02/05/08에 따라 Catalog, Scratch, backup, Native boot/recovery/read-only를 순정 경로로 구현한다. WAL/FULL/fullfsync pragma, 트랜잭션·checked close, 기존 Root 재오픈을 확인한다. 공간 소진 시 cleanup 예약 공간과 실패 재시도를 검증한다.
5. 제품·배포 수용 후 quanta-capacity-vfs feature/test-hooks, 심볼, Cargo patch 및 두 로컬 사본을 삭제한다. lockfile과 실제 바이너리에서 단일 SQLite links 소유자·버전·bundle/feature를 확인한다. 공용 close 유틸은 유지한다.

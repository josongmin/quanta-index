## 1. Decision in one paragraph

Keep environment variables as the deployment input and resolve them once into a typed, immutable `SearchdConfig`. Give the already-committed lexical/semantic index contracts and current query algorithm one explicit, versioned *logical* recipe/profile name each. Show and validate the resulting configuration before boot; record a redacted effective policy digest for diagnosis. Build-policy changes create a new sealed generation; a derivation-only cutover may reuse one only with complete provenance and compatibility proof. Runtime resource changes take effect after restart. V1 does not add a configuration server, general YAML parser, live reload, per-request tuning, arbitrary ANN parameters, or a new persisted profile field merely to duplicate existing seals.

This RFC distinguishes *which setting was requested*, *which value was resolved*, *where it was applied*, and *which sealed generation a query actually read*. A successful config parse is not a successful daemon boot, index build, or quality qualification.

## 2. Current behavior and exact seams

1. The release binary parses `serve [--state-root PATH]` or offline state commands at [runtime process entry](../../../crates/quanta-index-searchd-runtime/src/bin/quanta-index-searchd.rs) and [CLI command](../../../crates/quanta-index-searchd/src/cli/command.rs). `--state-root` overrides only root selection; all policy families still resolve through [SearchdConfig::from_lookup](../../../crates/quanta-index-searchd/src/app/config.rs). Offline migration/backup/restore/verify commands do not boot a serving config.
2. `SearchdConfig` applies `ENV_POLICY_FAMILIES`, checks required history retention and the combined memory envelope, and later [runtime assembly](../../../crates/quanta-index-searchd/src/app/runtime.rs) validates provider/grant and wires query, control and ingest servers. Query admission, resource budgets, caches, writer bounds and socket policy already have typed owners. The config tests check family membership, both root entry points and non-default wiring.
3. At the drafting snapshot, [semantic derivation](../../../crates/quanta-index-search-plane/src/semantic_derive.rs) read `QUANTA_INDEX_SEMANTIC_DERIVE_MODE` outside `SearchdConfig` with a fallback default. The typed-only cutover removes this selector. Recheck the concurrent Rust writer's final source before claiming it landed.
4. The [lexical seal](../../../crates/quanta-index-lexical/src/sealed_generation/seal.rs) commits the normalizer version and artifact set. The [semantic generation contract](../../../crates/quanta-index-semantic/src/generation_contract.rs) commits model ID/revision, dimension, normalization, distance and corpus policy. The [vector-index seal](../../../crates/quanta-index-semantic/src/manifest.rs) records ANN build parameters, actual coverage and query effort. [Vector-index open/query](../../../crates/quanta-index-semantic/src/vector_index.rs) verifies and applies that sealed effort; exact generations bypass ANN.
5. [Hybrid fusion](../../../crates/quanta-index-core/src/domains/hybrid/service.rs) fixes RRF `k=60` and its candidate policy in code. [QueryReadViewV2](../../../crates/quanta-index-search-plane/src/query_dispatcher/read_view/view.rs) already pins resource handles, artifact identities, normalizer and semantic model profile for a request. The public wire contract does not need another profile field for the first implementation.
6. [SDK `ClientProfile`](../../../crates/quanta-index-sdk/src/config.rs) means transport access (`Full`/`QueryOnly`). `just rust-profile` means build/test selection. Neither is a serving-quality profile.
7. The current `QUANTA_INDEX_PROVIDER_ENDPOINT` is copied into the egress grant, whose validation checks presence, while [OpenAI provider composition](../../../crates/quanta-index-searchd/src/app/runtime.rs) builds a provider with the [fixed public base URL](../../../crates/quanta-index-embed/src/openai.rs). It does not route to the grant endpoint or compare the two. This is an existing authorization/application mismatch, not a configurable endpoint feature.
8. [Activation promotion](../../../crates/quanta-index-search-plane/src/search_corpus_lifecycle.rs) proves the full pair and promotes the handles. [Query snapshot acquisition](../../../crates/quanta-index-search-plane/src/query_dispatcher/read_view/snapshots.rs) opens only requested tracks, and the semantic serving open checks sealed layout without rereading every dataset payload byte. A query policy gate must preserve this scope and proof level.

### Consequences of the current layout

- Parser validation and provider/network or state-root readiness are different proof levels. A future `config check` must say exactly which level it covers.
- OpenAI's operator-supplied `QUANTA_INDEX_EMBED_MODEL_REVISION` is a namespace/rotation commitment, not independent proof that the remote provider kept model weights immutable.
- The running daemon composes one query/corpus embedding identity. After a model switch, an older generation built with a different model may be preserved on disk but its semantic query cannot be promised to work with the new process. No multi-model serving is implied by this RFC.
- Existing harness `config_digest` values describe their own benchmark parameters. They are not automatically a digest of the full effective daemon configuration.
- The fallback derivation path and typed-source path can both commit generation-level `corpus_policy_digest=semantic-source.v1`. A matching corpus-policy digest alone does **not** attest that every row came from typed sources; a legacy fallback marker can live at narrower row/view scope.

## 3. Scope and setting classes

| Class | V1 examples | Owner and source | When changed | Required effect |
|---|---|---|---|---|
| Instance/runtime policy | socket paths/access; query slots/deadlines; writer, snapshot, regex, embedding-cache and stream budgets; retention; maintenance; provider retry/cost ceilings | existing `SearchdConfig` + env | startup only | validate composition, restart daemon; no generation rewrite solely for these |
| Ingest/content policy | typed semantic-source contract; producer-owned source/render policy; lexical normalizer and text-authority format; embedding model/revision/dimension/normalization | producer contracts and adapters own content truth; `SearchdConfig` selects provider | before a new build or typed-only cutover | new generation for changed content/model; prior-generation reuse requires complete typed provenance and gate approval; never reinterpret sealed bytes |
| Physical index policy | Tantivy schema/analysis; LanceDB ANN build recipe, library capability and coverage | adapter-owned code and existing seal | build/seal | new generation; delta inheritance only when its existing compatibility test accepts it |
| Query algorithm policy | current RRF and over-fetch; ANN effort from the opened generation's seal; exact/bounded outcome rules | core/search-plane/semantic adapter | process release; ANN effort selected by generation | one named built-in query profile; preserve request read pin and trace truth |
| Secret/authorization | `OPENAI_API_KEY`, egress grant, cursor key | secret source and existing grant/key owners | deployment restart or offline key workflow | never emit secret bytes in `show`, logs, digest inputs or benchmark artifacts |
| Dev/verification selection | `hash-dev`, `QUANTA_INDEX_ALLOW_DEV_EMBEDDER`, `just rust-profile` | existing dev/test front doors | explicit test invocation | cannot qualify learned production relevance |

`IndexBuildRecipeV1` (`index-build-v1`) and `QueryExecutionProfileV1` (`query-execution-v1`) are *typed views of these contracts*, not a new tunable registry. V1 ships one named recipe/profile of each. **Named profiles are immutable contracts: any behavior-affecting recipe or query-algorithm change MUST allocate a new version and name.** This includes changing fixed RRF `k`, over-fetch, analysis, ANN build defaults or applicability rules; an implementation refactor may retain the name only if equivalence is proved on its owning contract tests. Do not keep a V1 label while silently changing its behavior.

`index-build-v1` identifies the compiled build recipe, **not** a generation's full content identity. A deployment's resolved index policy also includes its selected model and producer content policy. The existing lexical/semantic seals attest what a particular generation actually contains. Do not infer that an old generation used `index-build-v1` merely because some fields look similar, or confuse its artifact digest with a recipe digest. `query-execution-v1` names the current compiled fusion/planning behavior; its ANN subpolicy is the selected generation's sealed effort, not an independently mutable query knob. A second named recipe requires a measured corpus and an explicit compatibility/release decision.

No `IndexBuildRecipeV1` string is added to persisted lexical or semantic formats: it would duplicate existing commitments. The **separate** typed-origin requirement below changes the semantic persisted row/manifest format **and the pre-seal generation-contract version**; that change prevents both old sealed rows and unfinished old staging tables from being resumed as typed-origin builds. Profile names in diagnostics are release claims tied to binary/source identity, not retroactive facts about old generations. The new format requires a candidate-root rebuild and an explicit old-binary/old-root rollback boundary.

## 4. Desired end-to-end application flow

```text
release env + secret injection + optional --state-root
  -> SearchdCommand (serve vs offline command)
  -> one SearchdConfig::resolve(input) [defaults, parsing, dependency checks]
  -> redacted effective view + nonsecret policy digest + fixed transport identity
  -> config check (pure preflight) OR runtime assembly
  -> provider/grant + state-root/lease + adapter capability checks
  -> one Config x Generation compatibility gate on verified generation evidence
  -> query/control/ingest servers under supervisor
  -> ingest: accepted producer contract -> build -> physical seal -> compatibility gate -> activation
  -> query: resolve active generation -> acquire QueryReadViewV2
            -> admit compatible opened handles -> execute sealed effort
            -> report pinned identity and actual outcome
```

### 4.1 Resolve and preflight

- Refactor only as needed so `serve`, `config check` and `config show` call the **same pure resolver**. The current `from_env`/`from_env_with_state_root` semantics, including `--state-root` precedence, remain unchanged. `config` is a distinct command branch; offline state commands remain isolated.
- `config check [--state-root PATH]` must parse every relevant env family, require the four history-retention limits, validate the memory envelope, embedder selection/revision, provider budget and complete egress grant when external egress is selected. For the current OpenAI implementation, trim the existing grant string and require it to equal the exported compiled base URL `https://api.openai.com` exactly; a path, alternate host, query, port or trailing slash is an unsupported endpoint, not a route selector. It must not create a state root, bind a socket, call a provider, migrate state or claim existing artifacts are readable. Return a nonzero exit and named field on failure; success says `CONFIG_VALID`, not `READY`.
- `config check --output json` has a versioned machine-readable result, including on invalid input: `{ "schema_version": 1, "status": "invalid", "issues": [{ "code": "MISSING_DEPENDENCY", "field": "embed_model_revision", "origin": "environment", "depends_on": "embed_provider" }] }`. `issues` is an array sorted by canonical field path and code; it may contain one issue if parsing fails early. Stable codes include `MISSING_REQUIRED`, `INVALID_VALUE`, `MISSING_DEPENDENCY`, `RESOURCE_BUDGET_EXCEEDED`, `INCOMPLETE_GRANT`, and warning-only `UNCLASSIFIED_ENV`. `field`/`depends_on` use canonical logical config paths, `origin` is `default|environment|cli`, and raw values are never needed in an issue. A valid result has `status=valid` and `issues=[]` unless warnings are present. Exit status is nonzero for invalid, zero for valid with warnings; JSON stays on stdout, operational diagnostics on stderr. Adding or changing code meanings requires a schema version change.
- `config show [--state-root PATH] --output json` uses the same resolver and emits schema version, profile names, effective nonsecret values and their `default|environment|cli` origins, digest and a `secret_status` such as `set|unset` where operationally useful. No `Debug` of `SearchdConfig`, raw environment dump, API key, cursor key or secret-derived digest. Human-readable output can be a separate renderer of the same typed view.
- Classify env names deterministically from a reviewed inventory: (1) daemon-owned keys in `ENV_POLICY_FAMILIES`; (2) explicitly cataloged build/CI/bench keys; (3) unclassified `QUANTA_INDEX_*` keys. The retired derive-mode name is not an accepted product override; release inventory must flag it. Known daemon-owned keys fail closed on malformed values. Known non-daemon keys are ignored by the daemon. Unclassified keys yield sorted `UNCLASSIFIED_ENV` warnings, never an accepted override; a release inventory checker must block them until classified. No such deploy wrapper is established in the audited source, so until the checker exists the release operator must explicitly review and record this inventory; do not claim automatic blocking. A `did you mean` suggestion may be displayed but is not a parsing or admission rule. Do **not** globally reject the prefix in a developer's daemon process.
- `EffectivePolicyDigestV1` hashes an explicitly enumerated, sorted map of resolved **nonsecret policy** values, including selected built-in profile names, provider kind, model identity/revision and the compiled fixed transport identity for OpenAI. It contains no selectable semantic derive mode. V1 adds no `QUANTA_INDEX_PROVIDER_CONTRACT_ID` or arbitrary route knob: the existing grant endpoint authorizes the fixed transport and must match it. Grant tenant/region/retention/profile/consent remain authorization inputs; the release receipt records their approved nonsecret identities under access control, while public `show` exposes status only. Raw URLs, tenant IDs, credential bytes and cursor keys are excluded from the digest and public `show`. `config check` cannot prove remote weight immutability, network reachability or an earlier deployment's identity. A future configurable route requires a separate versioned transport/grant contract, cache-identity and model-revision rotation rule, and end-to-end route proof before activation. An identical digest with different secret versions or authorization bindings is **not** evidence of an equivalent deployment.
- Use the accepted digest framing with domain `quanta-index/effective-policy/v1` and length-prefixed UTF-8 field name plus typed canonical value for each field; missing and present values are distinct. Freeze the exact included/excluded field inventory, type tags, numeric/boolean/optional encodings, sort order and test vectors **before** implementation emits the digest; an ad hoc JSON serialization is not a contract. Changing an *included* value must change the digest. Process-local paths, authorization/secret fields and runtime state are excluded and reported separately. The redacted view lists excluded field names and reports authorization fields as `configured|missing` without values. The digest is a comparison aid, not authentication, a complete process identity, or proof of provider model immutability.

### 4.2 Boot and apply

- Capture one environment/CLI input snapshot and resolve it once before any state-root mutation. `HOME`-based root fallback belongs to this injected resolver too, not a second ambient read. Remove the production derive-mode env reader and fallback selector; the materializer has one typed-source live path. Keep test construction explicit without exposing a production mode.
- Run the pure checks first, then the existing runtime checks: state format/lease, socket access, adapter open, provider grant, boot inventory and supervisor child startup. Enforce the fixed transport/grant endpoint equality at runtime composition too, including constructors that bypass the CLI preflight. No preflight receipt substitutes for those checks. A child or adapter failure retains the existing startup rollback/exit contract.
- Use one resolved config instance for the embedder, cache identity, provider budget, ingest/stream window, query admission and maintenance. Derive the expected corpus model identity from the typed profile and compiled constants **before** active-pair boot proof; validate it against the single actually built corpus provider before serving. For each usable query profile, verify the built query embedder's advertised ID/revision against that corpus provider too, then use that verified query identity in pre-embedding admission. `unavailable` retains its existing hash corpus identity and unavailable query behavior; semantic queries keep the provider-unavailable refusal without provider I/O. The new local `potion-code` profile uses its compiled pinned asset identity and still verifies model files at runtime. No provider/network I/O is allowed in `config check`. Do not reread product env variables downstream; classify current benchmark/crash/test-only reads separately. The boot notice and `config show` report the effective policy digest, selected profile names and the typed-source contract identity; never report secrets or add one metric label per arbitrary config value.

### 4.3 One Config × Generation compatibility authority

Define one pure `GenerationCompatibility::check(&ResolvedGenerationPolicyV1, &GenerationAdmissionEvidenceV1) -> Result<CompatibilityReceiptV1, CompatibilityErrorV1>`. `ResolvedGenerationPolicyV1` is the generation-relevant projection made once from `SearchdConfig` plus the compiled recipe/profile identities; the search-plane must not import a daemon config type or read env. Evidence is explicitly scoped as `FullPair` for lifecycle admission or `DeclaredDomains` for a query read view. Both carry the exact pin, checked track identities, concrete seal-backed fields, model contract, backend capabilities and sealed typed-origin counts; semantic `DeclaredDomains` also carries the **observed query embedder ID/revision** from the dispatcher provider port, read before I/O. A `DeclaredDomains` result is never a full-pair receipt. The adapter's existing deep `open_proven` supplies lifecycle physical proof; a query cold-open supplies only its existing sealed-layout/open proof and must not be described as a full dataset-byte proof. An unverified manifest field or operator-supplied profile label cannot stand in for either evidence scope.

- The check is the only owner of policy-versus-generation rules: model/revision/dimension/normalization and semantic content policy for semantic evidence, lexical normalizer for lexical evidence, policy-level ANN applicability, full composite root binding for lifecycle admission, and sealed typed-origin counts for every typed-only semantic track. For query semantic evidence it uses the **actual verified query embedder identity**, not just a projected corpus model; the `unavailable` sentinel retains its provider-unavailable refusal. Persisted lexical format and physical ANN consistency remain adapter-open responsibilities; do not duplicate those validators in the policy gate. Fixed transport/grant equality is a config/composition check: current generation seals do not attest which external endpoint produced the vectors. Runtime capacity, secrets and paths are not generation compatibility fields. A returned receipt binds exact policy/profile identity, generation artifact digests, requested scope and checked evidence; the deployment receipt separately binds binary/source identity. The compatibility receipt is a decision record, not a substitute for physical seal verification or a reusable success token after those identities change. Missing *required* evidence is incompatibility, not permission.
- Call this same function after each route's existing adapter proof and **before** serving-open admission, activation promotion, restart rehydration and rollback. Candidate-root cutover reuses activation and restart proof **in the isolated candidate daemon**; no separate offline checker or imaginary `verify-state` policy gate is required. The existing [pair proof owner](../../../crates/quanta-index-search-plane/src/search_corpus_lifecycle.rs) already combines activation, rollback and restart physical opens; extend that shared seam rather than adding separate predicates to each command. The [read-view owner](../../../crates/quanta-index-search-plane/src/query_dispatcher/read_view/view.rs) acquires only declared domains, so a lexical-only historical query must not cold-open semantic merely to satisfy a pair-shaped check. Check exactly the acquired track evidence against its pinned generation before `QueryReadViewV2::assemble`, including resident snapshot hits; never infer policy admission from registry presence alone. A query may reuse an admitted pinned handle only while its bound policy/generation identity is unchanged.
- Keep failure domains distinct. A corrupt/missing physical seal follows the adapter's existing quarantine/open refusal. An intact generation incompatible with the current policy is a typed policy refusal and must **not** quarantine or rewrite the artifact; an old binary/config may still read it. No fallback to a weaker route, old model or unchecked ANN settings. `config check` cannot call this function because it has no verified generation evidence; its result stays `CONFIG_VALID`, not `READY`.

Under the typed-only cutover, a prior generation may be reused **only** if typed-source origin is sealed for its complete live row set. The existing generation-level `semantic-source.v1` policy digest is insufficient because a fallback batch can carry the same digest; `render_policy_digest` is producer-controlled and is not an exclusive typed-origin marker. V1 therefore adds a search-owned `typed|legacy_fallback|unattested` origin to each newly written semantic row, includes it in a versioned semantic row root, and seals aggregate origin counts with `row_count` in the semantic manifest. The origin is stamped by the derivation path, never accepted from a producer string. At seal, scan the complete live row set after replacement/tombstone/delta inheritance; assert counts sum to `row_count`. The existing physical seal binds the manifest and dataset. Strict admission requires `typed == row_count` and both other counts zero, including for empty or inherited generations, without a per-query full scan. Old generations lacking the field are `unattested` and cannot be relabeled; rebuild them in a separate candidate root under the new format. The row root still commits each row's producer-supplied source/render digests, but that proves what Quanta received, not that the producer's source was semantically correct. Producer source truth remains a separate qualification claim. No mutable sidecar, copied CI receipt or unverified producer assertion grants admission.

### 4.4 Ingest, seal and activation

- The producer remains owner of source/render truth. Search-corpus `preflight_batch` validates typed semantic-source coverage and producer shape **before** provider I/O, index writes or the fenced apply. The operation journal may still durably prepare or record a typed refusal under its existing idempotency contract; do not claim zero state mutation on that path. Existing batching and lifecycle fences remain authoritative.
- Runtime budget changes affect work admission, not source identity. Changed content, model, lexical analysis or ANN build policy must build/seal a new generation. Typed-only cutover may reuse an unchanged generation only under the complete provenance rule in §4.3. The seal continues to record concrete fields and actual backend attestations; the logical profile name cannot make an incompatible artifact acceptable.
- A delta may reuse its base only when every required content, model and physical-index property is attestable by the compatibility authority and existing adapter checks. Its copied rows retain their sealed origin; replacement and tombstone operations change the final live-row counts before seal. A base without the new origin field cannot be inherited into a strict-compatible generation. If proof is missing or the profile changes incompatibly, rebuild from the producer's authoritative source in a new root. Do not relabel or patch a sealed generation.
- Activation occurs only after the new generation is durable, physically verified, compatible with the resolved generation policy and jointly ready for its declared query routes. `config show` never activates anything.

### 4.5 Query and result truth

- A request resolves its generation and acquires the existing read view before reading search data. The serving-open admission must have passed the same compatibility authority against the process's resolved policy; the query path uses the opened generation's actual ANN effort and model contract. The query profile cannot override the seal, access an ambient latest index or silently substitute hash embeddings.
- V1 keeps RRF and over-fetch fixed. Expose their built-in profile name in process diagnostics and benchmark provenance. Existing read identity, dense effort and explain traces remain the per-request proof; no wire DTO addition is required merely to print a profile name.
- If a later experiment introduces a second query profile, validate it against the selected generation, bind it once per request and make it visible in response/explain and continuation context. That future wire/cursor change requires its own versioned contract review and SDK/CLI proof. It is not implicit V1 work.

## 5. Change and rollout matrix

| Operator change | Preflight | Cutover | Old generation / rollback boundary |
|---|---|---|---|
| Capacity, cache, deadlines or retention | `config check`, capacity sizing, restart smoke | restart with same root under existing lease/supervisor contract | no semantic rebuild; retention reduction can reclaim old generations, so check pin/rollback window before applying |
| Secret rotation, same provider/model identity | complete grant and credential availability; network call is separate proof | restart and opt-in real-provider smoke | effective policy digest can remain equal; record secret *version/reference* in deployment receipt outside public config output, never secret bytes |
| Provider endpoint/routing change, even if model name stays the same | outside V1; a grant endpoint different from the compiled OpenAI transport is invalid before egress | no V1 routing cutover; require a separate versioned transport/grant and model/cache migration design | unchanged model/revision strings do not prove equivalent embeddings; changing only the grant text must not authorize another route |
| Typed-only semantic source cutover | producer typed-source coverage plus sealed typed-origin counts for every live semantic row | refuse chunk-only batches; reuse only a new-format generation with `typed == row_count`, otherwise rebuild from typed input in a candidate root | matching `semantic-source.v1` alone is insufficient; an old or legacy-built generation is refused, not relabeled |
| Model ID/revision/dimension/content policy | provider grant + pinned source corpus + cost budget + judged quality evidence | drain ingest, preserve old root/config, build a separate candidate root or offline candidate, verify pair, then controlled binary/config/root cutover | current daemon serves one embedding identity; old-model semantic generations may be unreadable by the new process. Pre-write rollback means old binary/config/root; after new writes, rollback needs an explicitly verified replay/translation path, otherwise roll forward |
| Lexical normalizer or storage format | lexical compatibility/migration audit | new build and activation or offline root migration as format requires | current lexical open refuses mismatched normalizer/format; do not promise live mixed-version reads |
| ANN build recipe/library | exact-vs-ANN and incremental reuse measurements; backend capability proof | build and seal a new generation, verify manifest and dataset agree | old generation serves only if the new binary actually opens/verifies its recorded seal; library version text alone is not a refusal or compatibility proof |
| Future query profile | held-out relevance and tail-cost evidence | versioned release; generation compatibility validation | rollback to prior binary/profile only where its wire/cursor and stored generation contracts still hold |

For model/content cutover, a second state root or offline candidate is a **procedure to build and verify**, not a new dual-running product feature. The existing process lease means two daemons do not write one root. If no staging root, producer replay, or qualified rebuild is available, mark the production cutover blocked rather than claiming a zero-downtime switch.

The deployment identity is the tuple `{binary/source identity, EffectivePolicyDigestV1, state-root identity, active composite generation inventory}` at a stated observation time. The state-root member is the existing canonical root identity under operator access controls, not a public config value; the generation member is a repo/revision-to-sealed-pair map, not one global counter. Activation changes this tuple even if the binary and config stay fixed. No individual member, including the digest, proves the running search state. The protected deployment receipt also records the compiled fixed provider transport identity, checked egress-grant identity, secret reference/version and each activated generation's sealed typed-origin evidence; secrets and raw endpoints do not enter public diagnostics.

## 7. Validation and release evidence

Owner-local tests:

- One table-driven case per env family: unset, explicit default, valid override, zero/boundary, malformed/non-Unicode, dependent-pair failure. Both root entry points and `config check/show` resolve equivalent policy values.
- Assert immutable profile names against fixed RRF/over-fetch and index-build recipe contract vectors; a behavior-changing test fixture with the old V1 name fails the owning release contract test. A refactor retaining V1 proves equivalence on those vectors.
- Deliberately mutate each *included* resolved nonsecret value, including provider kind/model revision, and assert the digest changes; excluded paths, grant identities, secret bytes, tenant IDs and raw endpoints never occur in the digest input or public JSON/stderr. Identical resolved values from explicit/default env have the same policy digest; provenance is displayed separately. A mismatched grant endpoint fails both preflight and direct runtime composition before provider I/O; a secret rotation may preserve the policy digest but changes the protected deployment receipt's secret reference/version.
- Parse `config check --output json` as schema V1 for valid, invalid and warning-only input. Assert stable code/field/origin/dependency, deterministic ordering, nonzero invalid exit, no raw invalid secret/endpoint echo and correct stdout/stderr separation. Known daemon, cataloged non-daemon and unclassified env keys have distinct outcomes; a close spelling suggestion cannot change admission. The release inventory checker blocks unclassified keys in a supplied release env fixture.
- `config check/show` in an empty temporary root creates no files/sockets and never calls a provider. Pure check reports `CONFIG_VALID`; runtime error reports retain their existing exit semantics.
- Typed-source derivation applies identically through serve and explicit-root paths; downstream materializer has no derive-mode env read. Hash-dev remains explicit, OpenAI revision/grant remains mandatory and `unavailable` behavior remains truthfully reported.
- The built-in recipe name and each generation's concrete lexical/semantic seals are reported separately; actual model/normalizer/ANN effort matches those seals, and a contradictory seal or unsupported model is refused. Delta reuse and fresh rebuild use the same compatibility rule. A physically valid but policy-incompatible generation is refused without quarantine; corrupt physical evidence still follows the adapter quarantine path. Pair activation and both resident/cold query opens give the same policy verdict for the evidence they each require; a lexical-only historical query does not open or gate semantic.
- Prove sealed typed-origin counts across replacement scopes, tombstones and delta ancestry. A fallback-built generation with the same `semantic-source.v1` policy digest, an old-format generation without origin, a mismatched count or a copied/tampered seal is refused for the typed-only cutover. A fresh generation without the new origin column is also refused. The same `GenerationCompatibility::check` verdict is observed at serving-open, activation, restart and rollback; candidate-root activation/restart exercise those same paths.
- Prove an incompatible historical semantic generation fails before the query embedder is called on both resident and cold paths, preserving the existing typed model-mismatch code; lexical-only history remains queryable without a semantic open. Query-open policy proof must not be reported as the activation path's deep dataset-byte proof.

Integration scenarios:

1. Start the daemon with a constrained query/memory/provider config; observe accepted/refused requests and boot identity, restart with a changed capacity value, and verify the new limit while the sealed generation identity is unchanged.
2. Typed-source and legacy-only producer batches under typed-only intake: accepted typed sources or typed refusal as specified; no provider call or index write for a rejected batch. Assert the existing idempotency journal's prepared/refused/replay result independently.
3. Build/seal/restart/query a generation, inspect lexical/semantic profile evidence and ANN effort; tamper a committed field to prove fail-closed open.
4. Change model revision with the same model name and attempt to query an older semantic generation; prove the model gate refuses. Build a fresh generation, verify cache namespace separation and query success. Do not count a hash/stub provider as production relevance proof.
5. Rebuild with an ANN recipe change; verify old/new seal ownership and exact-vs-ANN quality on a qualified corpus. Check incremental reuse remains within the policy's compatibility/budget proof.
6. Rehearse a candidate-root cutover and pre-write rollback with old binary/config/root. Test the post-write replay path only if one is actually implemented and verified; otherwise record the roll-forward boundary.
7. Under the typed-only cutover, attempt activation/restart with a fallback-built but otherwise valid generation, an old-format generation and a semantic-manifest V11 generation with copied/tampered origin counts. All refuse without quarantining an intact policy-incompatible artifact; physical tampering still follows the adapter corruption path. A correctly bound typed-only manifest V11 generation passes activation, restart, rollback and historical semantic serving-open.
8. Capture a deployment receipt before and after activation: binary/source and effective policy digest stay fixed, while active generation inventory changes. Verify the canonical root and artifact identities identify the candidate actually served; a matching digest alone must not be reported as deployment equivalence.
9. Exercise semantic, hybrid, hybrid-seed and explain routes against an incompatible historical semantic generation with a counted embedder; all refuse before provider I/O. A lexical-only historical route remains available under its own compatible lexical evidence. Repeat once with promoted resident handles and once after eviction/cold-open.

Rust implementation verification uses the repository front door: owner-scoped `./scripts/cargow test -p <crate>` or registered `just rust-profile` scopes, then `just rust-profile test-integration`, `just rust-profile test-daemon`, and final `just rust-profile verify-rust` on a stable source. CLI/public-wire changes additionally run their owning CLI/public-API/fuzz rails. Record command, HEAD/dirty-source digest, selected/executed count, result and excluded surface; a dirty or older receipt is not exact-source release proof. Real-provider and judged relevance are opt-in owner-local qualifications with model, corpus, host and cost recorded; synthetic/hash runs prove mechanics only.

Release acceptance requires one reviewed redacted effective config, proved fixed-transport/grant equality for external embedding, source-bound profile/compatibility and sealed typed-origin evidence for every affected activated generation, a completed candidate-root activation/restart/cutover receipt for the semantic format change, and measured relevance/latency/resource results for any *new* quality profile. Parser/boot green alone cannot approve a search-quality claim. A candidate-root rehearsal that has not been run is recorded as missing evidence, not a passed machine gate.

## 8. Deliberate limits and follow-on trigger

- V1 has one built-in index policy and one built-in query policy. It does not offer live mutable profiles, per-tenant profiles, cluster-wide config propagation, arbitrary field-level ANN settings, or multi-model serving in one daemon.
- V1 also does not add an OpenAI-compatible endpoint selector. The current fixed transport/grant mismatch is repaired by equality validation; changing the actual route is a separate contract and migration.
- A second profile is justified only by a fixed corpus and SLO showing a useful tradeoff, with a complete build/query compatibility rule and rollback route. `nprobes`, `ef` and refine effort affect recall and latency; changing them requires measured evidence rather than a free env knob.
- A versioned config file becomes useful only if environment management cannot express reviewed deployments. If added, it must feed the **same** typed resolver and declare explicit precedence; a second parser or hidden overlay is rejected.
- `config show` is an operator diagnostic, not a secret inventory or readiness endpoint. A deployment receipt separately records the secret reference/version and actual binary/root/source identity under its access controls.

## 9. External design references

- [Elasticsearch index settings](https://www.elastic.co/docs/reference/elasticsearch/index-settings): separates static index-creation settings from dynamic settings. This RFC applies the distinction to sealed generation versus restart-scoped process policy; it does not copy Elasticsearch's dynamic API.
- [OpenTelemetry configuration data model](https://opentelemetry.io/docs/specs/otel/configuration/data-model/): typed/schema-described resolved configuration and explicit parsing boundary motivate a single resolver and inspectable effective view.
- [Kubernetes ConfigMap](https://kubernetes.io/docs/concepts/configuration/configmap/): env-injected configuration requires process restart to observe updates, matching the V1 startup-only deployment contract.
